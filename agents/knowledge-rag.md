# 🧠 Knowledge & RAG Engineer — 전 에이전트 지식 증강(RAG) 레이어

> 소속: DTx 도박중독 오케스트라 | 보고: Orchestrator
> **임무:** 각 에이전트가 자기 전문지식을 *기억에 의존*하지 않고 **권위 있는 출처에서 검색(Retrieve)해 근거와 함께 생성(Augment·Generate)**하도록 만든다.
> **근거 논문:** [RAG (Lewis 2020)](../references.md#r1) · [MedGraphRAG (Wu 2024)](../references.md#r2) · [Agentic RAG-Reasoning Survey (Li 2025)](../references.md#r3)

---

## 0. 왜 RAG인가 (이 프로젝트에서)

| 문제 | 순수 LLM/파인튜닝 | RAG |
| --- | --- | --- |
| 규제·임상 사실 정확성 | 환각 위험, 출처 불명 | **출처 인용(provenance)**으로 검증 가능 [R1] |
| 지식 갱신(가이드라인 개정 등) | 재학습 필요 | **문서만 교체**하면 즉시 반영 [R1] |
| 의료 안전성 | 근거 없는 단정 | **근거기반(evidence-based)·감사가능** [R2] |
| 복잡 추론(왜 갈망이 오르나) | 단발 답변 | **검색⇄추론 반복**으로 심층 분석 [R3] |

> Lewis(2020)의 핵심: 파라미터(머릿속) 기억 + **비파라미터(외부 문서) 기억**을 결합하면 지식집약 과제에서 더 정확하고, *결정의 출처를 댈 수 있다*. [R1]
> 본 앱은 **SaMD(의료기기)**라 "출처를 댈 수 있음"이 곧 안전·규제 요건이다.

## 1. 두 층위의 RAG

```
(A) 빌드타임 RAG — 설계/개발 시, 각 에이전트가 권위 문서를 검색해 설계 근거로 삼음
(B) 런타임 RAG  — 출시된 앱의 AI 코치가 환자·임상가 질의에 근거기반으로 답함 (MedGraphRAG)
```

둘 다 동일 원리(검색→통합→생성+인용)지만 코퍼스와 안전요건이 다르다.

## 2. 🗂️ 에이전트별 지식 베이스 & 검색 전략 (빌드타임 RAG)

> 각 에이전트는 아래 **전용 코퍼스**를 벡터/그래프 인덱스로 보유하고, 답변·설계 시 **반드시 출처 청크를 인용**한다.

| 에이전트 | 지식 코퍼스(검색 대상) | 검색 전략 | 핵심 산출에 적용 |
| --- | --- | --- | --- |
| 🎯 **Orchestrator** | 6개 에이전트 SSOT 문서 + ADR 결정로그 | **Agentic 라우팅**(중앙집중 매니저) [R3] | 질의를 적합 에이전트로 분배·종합 |
| 🏛️ **System Architect** | Flutter/DRF/PostgreSQL/TimescaleDB/K8s 공식문서, CSAP·ISMS-P 지침 | Dense 검색 + 재랭크 [R1] | 기술결정 근거·트레이드오프 |
| 🎨 **Frontend/UX** | WCAG 2.2, Flutter API, 행동변화·MBRP(충동 파도타기) UX 문헌 | 쿼리 재구성 후 검색 [R3 §3.1] | 접근성·치료적 UX 패턴 |
| 🗄️ **Backend/Data** | 식약처 DTx 데이터 가이드, IEC 62304, FHIR, DB 문서 | Dense + 메타필터(규제 태그) | 스키마·심사 데이터 항목 |
| 📱 **Native Integration** | Apple FamilyControls/Screen Time·WWDC, Android Accessibility·Play 정책 | 플랫폼 버전 필터 검색 | 권한·정책 준수 근거 |
| 🩺 **Clinical & Safety** | **MedGraphRAG 3계층**(아래 §3) | **U-retrieve + 출처인용** [R2] | 임상근거·안전·규제(최고 엄격도) |

> 공통 원칙(Survey의 RAG 3단계 [R3 §2]): **① 검색(Retrieval) → ② 통합(Integration: 중복제거·충돌해소·재랭크) → ③ 생성(Generation: 근거에 정합한 답+인용)**.

## 3. 🩺 Clinical & Safety의 MedGraphRAG (안전·근거 핵심)

도박중독 앱은 **갈망을 의도적으로 유발**하므로, 임상·안전 관련 모든 출력은 *근거가 추적되어야* 한다. MedGraphRAG[R2]를 그대로 적용한다.

### 3.1 3계층 계층형 의료 그래프 [R2 §2.1]
```
[1단계] 사용자/기관 제공 자료 ── 우리 임상 프로토콜·동의서·기관 지침(사설 데이터)
            │ 엔티티 추출·연결
[2단계] 권위 의학 문헌 ──────── 중독의학·CBT/ERP·MBRP(Urge Surfing)·GA 논문/교과서
            │
[3단계] 기초 의학 사전 ───────── UMLS·표준 용어사전(용어 정의·의미관계)
```
→ 모든 응답이 **1→2→3 출처로 역추적** 가능 → 임상가가 직접 감사(audit)·교정 가능 [R2].

### 3.2 시맨틱 청킹 [R2 §2.1]
- 토큰/글자 고정분할 대신 **명제 변환(proposition transfer)** + **5문단 슬라이딩 윈도우**로 주제 일관 청크 생성 → 맥락 손실 방지.

### 3.3 U-retrieve (탑다운 검색 + 바텀업 생성) [R2]
```
질의 → 의료 태그로 구조화 → (탑다운) 그래프 인덱싱으로 관련 메타그래프 검색
     → TopK 관련 노드·관계 수집 → (바텀업) 요약·생성 → 답변 + 인용
```
> 전역 맥락 인지와 LLM 컨텍스트 한계 사이 균형을 유지. [R2]

### 3.4 안전 가드레일 (의료 RAG 필수)
- **무근거 시 단정 금지** → "근거 없음/전문가 상담(1336)" 폴백.
- 모든 임상 주장에 **출처 인용 의무**(intrinsic citation) [R2].
- 범위 한정: AI 코치는 *지지적 코칭*만, 진단·처방 금지 → Clinical&Safety veto.
- 위기 신호 감지 시 RAG 답변보다 **1336/109 에스컬레이션 우선**.

## 4. 🎯 Orchestrator의 Agentic RAG (검색⇄추론) [R3]

### 4.1 오케스트레이션 패턴 = 중앙집중 멀티에이전트 [R3 §5.2]
```
        사용자/임상가 질의
              │
        🎯 Manager(Orchestrator)  ← 질의 의도 분해·라우팅
        ┌─────┼─────┬─────┐
       🏛️    🗄️    📱    🩺   ← Work Agents(각자 RAG)
        └─────┴──┬──┴─────┘
              종합·충돌해소·근거통합 → 답변
```
Survey의 분류 중 **Centralized Multi-Agent**(매니저+작업에이전트)가 우리 구조와 정확히 일치 [R3 §5.2].

### 4.2 검색-추론 시너지 [R3 §5]
- 단순 사실 질의 → **RAG→Reasoning**(검색 후 추론).
- 복잡 질의("세션 많은데 갈망이 왜 오르나") → **Synergized RAG⇔Reasoning**: 추론이 검색을 유도하고, 검색결과가 추론을 정교화하는 **반복 루프**(Deep Research식) [R3 §5].
- 추론 워크플로 선택: 단순=Chain, 분기가설=Tree, 다출처 관계=**Graph**(MedGraphRAG와 결합) [R3 §5.1].

## 5. 🏗️ 아키텍처 추가물 (기존 스택 재사용)

| 구성 | 선택 | 비고 |
| --- | --- | --- |
| 벡터 인덱스 | **pgvector**(기존 PostgreSQL 확장) | 별도 DB 없이 Dense 검색 [R1] |
| 그래프 저장 | Neo4j 또는 pgRouting/Apache AGE | MedGraphRAG 3계층 그래프 [R2] |
| 임베딩 | 한국어 특화 임베딩 모델(예: KURE/bge-m3) | 한국어 임상·앱 텍스트 |
| 검색 파이프라인 | 쿼리 재구성→검색→재랭크/필터→통합→인용생성 | Survey 3단계 [R3 §2] |
| 가드 | 근거 없음→폴백, 인용 강제, 위기 우선 | 안전 |

> 런타임 코치 RAG는 **임상가용**(근거 인용 강한 어시스턴트)과 **환자용**(비낙인·지지적, 위기 시 1336)으로 분리하고, 둘 다 Clinical&Safety 코퍼스를 공유한다.
