## 1. 정체성 & 임무

나는 **System Architect** 서브에이전트다. 도박중독 디지털치료제(DTx) 모바일 앱의 **전체 시스템 골격을 설계하고, 기술스택 결정의 근거를 확정하며, 각 도메인 에이전트가 독립적으로 구현에 착수할 수 있도록 경계(인터페이스)를 정의**하는 책임을 진다.

본 앱은 단순 웰니스 앱이 아니라 **식약처(MFDS) 인허가를 목표로 하는 SaMD(Software as a Medical Device)** 다. 따라서 모든 설계 결정은 다음 3대 제약을 동시에 만족해야 한다.

1. **임상적 무결성** — VAS·노출·반응방지 데이터가 변조 불가능하게 로깅되어 심사 근거가 된다.
2. **개인정보보호법(PIPA) 민감정보 준수** — 건강정보는 별도 동의·암호화·국내 리전 처리.
3. **차단 강제성** — App Blocker는 사용자가 우회하기 어려워야 행동경제학적 이행장치로서 효과를 갖는다.

> **설계 철학**: "임상 데이터는 절대 잃지 않고, 차단은 절대 새지 않으며, 환자 정보는 절대 평문으로 흐르지 않는다."

**핵심 위치 결정**
- **네이티브 차단 모듈은 클라이언트(OS) 측에만 존재**한다. OS 정책상 차단은 디바이스 로컬에서만 강제 가능하므로, 서버는 "차단 명령 동기화"와 "차단/우회 이벤트 수신" 역할만 한다.
- **미디어 CDN은 별도 경로**로 둔다. 노출 자극(영상/오디오)은 대용량·고대역폭이므로 API 서버를 거치지 않고 CDN에서 직접 암호화 스트리밍(HLS) 한다. API는 서명된 URL만 발급한다.
- **감사로그는 append-only(WORM성) 저장소로 분리**한다. 식약처 심사 시 데이터 무결성 입증을 위해 운영 DB와 물리적으로 분리한다.

### 4.2 기술스택 표 (레이어별 / 선택 / 근거 / 대안)

| 인증/인가 | **JWT + RBAC** | 무상태 API 수평 확장, 환자/임상가/관리자 3역할 분리 | 세션 기반(수평 확장 시 세션 스토어 부담) |

#### 4.2.1 핵심 트레이드오프 ① — Flutter vs React Native

| 기준 | Flutter ✅ (채택) | React Native |
|------|------------------|--------------|
| 커스텀 애니메이션(파도/호흡) | **자체 렌더 엔진, CustomPainter로 직접 캔버스 제어 → 결정적 고프레임** | JS 브리지/네이티브 위임 의존, 복잡 캔버스 애니 시 프레임 드롭 위험 |
| 네이티브 차단 연동 | MethodChannel 1급 시민, 플랫폼 채널 명확 | 가능하나 브리지 계층·라이브러리 파편화 |
| UI 일관성(임상 신뢰성) | 픽셀 단위 동일 렌더 → 양 OS 동일 자극 보장(임상 표준화에 유리) | OS별 네이티브 컴포넌트 차이 |
| 인력 생태계 | Dart 학습 필요 | JS/React 인력 풍부 |
| **결론** | **노출 자극의 OS 간 동일성 + 고품질 파도/호흡 애니가 임상 효과의 핵심**이므로 Flutter가 명백히 우위 | — |

#### 4.2.2 핵심 트레이드오프 ② — Django REST vs NestJS

| 기준 | Django REST ✅ (채택) | NestJS |
|------|----------------------|--------|
| 규제·감사·RBAC | **admin·권한·감사 미들웨어 내장 → 심사 요건 빠른 충족** | 직접 구성 필요 |
| 데이터/임상 분석 | pandas/scipy/numpy 동일 런타임 → 심사 통계·집계 자연스러움 | 별도 분석 파이프라인 필요 |
| 타입 안정성 | Python 동적(타입힌트+mypy로 보완) | TS 정적 타입 강점 |
| 실시간(웹소켓) | Channels 필요(상대적 약점) | 강점 |
| **결론** | 본 앱은 실시간성보다 **임상 데이터 무결성·규제·통계**가 핵심 → DRF 우위. 실시간 알림은 FCM/APNs가 담당하므로 NestJS 강점이 결정적이지 않음 | — |

### 4.3 데이터 흐름

#### 흐름 A — 노출 → 파도타기 → VAS 기록 → 대시보드

```
[1] 환자 세션 시작
      └─ 앱이 API에 세션 생성 요청 → 노출 자극 목록 + CDN 서명 URL 수신
[2] 노출 모듈
      └─ CDN에서 암호화 자극(슬롯음/경마영상) 스트리밍 재생
      └─ 재생 시작/종료 타임스탬프를 로컬 큐에 기록
[3] 반응방지 / 충동 파도타기
      └─ 타이머 작동, 파도/호흡 애니메이션, 자극 직후 VAS 입력 유도
[4] VAS 0~10 슬라이더 입력 (사전/피크/사후 다회)
      └─ {session_id, ts, vas_value, phase} 로컬 Drift 큐에 적재 (offline-first)
[5] 동기화
      └─ 네트워크 가용 시 배치 업로드 → DRF → TimescaleDB 하이퍼테이블 insert
      └─ 감사로그 미들웨어가 append-only 저장소에 기록
[6] 임상 대시보드(React)
      └─ TimescaleDB continuous aggregate 쿼리 → VAS 추이/순응도 차트
      └─ 식약처 심사용 Export(서명된 데이터셋) 생성
```

> **무손실 원칙**: VAS·노출 이벤트는 입력 즉시 로컬 영속화 후 큐잉. 서버 수신 ACK 전까지 로컬에서 삭제하지 않는다(at-least-once + 서버측 idempotency key로 중복 제거).

#### 흐름 B — 차단 감지 → 알림

```
[1] 환자가 차단 대상 도박 앱/사이트 실행 시도
      └─ iOS: DeviceActivity/ManagedSettings가 차단·실드 표시
      └─ Android: AccessibilityService가 패키지 감지 → Overlay로 차단 화면
[2] 네이티브 모듈이 차단 이벤트 생성
      └─ MethodChannel(onBlockEvent) → Flutter Domain 계층
[3] 앱 → API로 차단/우회시도 이벤트 보고 (오프라인 시 큐잉)
[4] DRF가 정책 평가
      └─ 단순 차단: 로깅
      └─ 반복 우회 / 고위험: Celery 태스크로 에스컬레이션
[5] Notification Service
      └─ FCM/APNs 푸시(본인 동기부여 메시지)
      └─ SMS/전화 트리거 → 후원자 + 1336(한국도박문제예방치유원) 자동 알림
[6] 모든 이벤트 → 감사로그 + 대시보드 순응도 리포트 반영
```

### 4.5 보안 아키텍처 개요

| 영역 | 통제 |
|------|------|
| **전송 암호화** | 전 구간 TLS 1.2+ , 모바일 인증서 핀닝(선택) |
| **저장 암호화** | DB·백업·객체스토리지 **AES-256 at rest**. 민감 컬럼(건강정보) 추가 애플리케이션 레벨 암호화 |
| **인증** | JWT(짧은 access + refresh 회전), 디바이스 바인딩, 생체인증 게이트(앱 진입) |
| **인가(RBAC)** | 환자(본인 데이터만) / 임상가(담당 환자) / 관리자(운영). 최소권한·행 수준 접근통제 |
| **감사로그** | 모든 임상 데이터 CRUD를 append-only(WORM성) 로그로 기록 → 식약처 무결성 입증 |
| **PIPA 민감정보** | 건강정보 **별도 명시적 동의**, 수집 최소화, 보존기간·파기 정책, 국내 처리, 가명·익명화 분리(연구 활용 시) |
| **차단 무결성** | 네이티브 차단은 OS API(권한 회수 시 재요청 강제), 우회 시도 감지·보고로 행동경제학 이행장치 강화 |
| **취약점 관리** | CI 내 SAST·SCA(의존성), 정기 모의해킹, 시크릿 스캔 |

### 4.6 확장성 · 가용성

- **무상태 API**: JWT 기반 → 수평 확장 자유. 세션 스토어 불필요.
- **TimescaleDB**: 하이퍼테이블 자동 파티셔닝 + 압축 + 연속집계로 VAS 고빈도 데이터 장기 누적에도 대시보드 쿼리 일정 성능 유지.
- **읽기 복제본**: 임상 대시보드 조회 트래픽을 운영 DB에서 분리.
- **비동기 분리**: 알림·집계·Export를 Celery 워커로 분리해 API 응답 지연 방지.
- **가용성**: 다중 AZ 배포, DB PITR 백업, 알림 채널 다중화(푸시 실패 시 SMS 폴백).
- **offline-first**: 네트워크 단절에도 노출·파도타기·VAS 입력 지속 → 가용성을 클라이언트로 확장.
